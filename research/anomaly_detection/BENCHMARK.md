# 이상탐지 평가셋

## 먼저 확인할 내용

기본 6개 평가셋은 **각각 이상 사례 5,000개**, 혼합 Hard는 **1,000개**다.
이상 사례는 총 **31,000개**이며, 대응 정상 대조군 **31,000개**는 별도다.
Process 행 수와 사례 수는 다르다. 정확한 행 수는 `scenario_summary.csv`에서 확인한다.

| 폴더 | 이상 사례 수 | 한 사례의 의미 |
|---|---:|---|
| individual_delay | 5,000 | 한 Process의 조건부 지연과 주변 정상 실행 |
| group_delay | 5,000 | 업무 집단 여러 실행의 동시 지연 |
| column_relation | 5,000 | 처리량–소요시간 관계를 어긋나게 만든 실행 묶음 |
| time_burst | 5,000 | 정상 전후 구간과 요청 집중 구간 |
| input_stop | 5,000 | 입력이 예상되는 구간에서 실행이 사라진 사건 |
| gradual_degradation | 5,000 | 정상 전후 구간과 점진적인 지연 증가 |
| mixed_hard | 1,000 | 위 6유형을 모두 포함한 독립 시계열 사례 |

모든 관측·정상 Process 및 검증용 Transaction의 STATUS는 S다.
정답은 **어떤 장애를 주입했는지**를 나타낸다. S라고 해서 정상이라는 라벨을 붙이지 않는다.
반대로 주입하지 않은 S 원본이 실제 운영에서 모두 정상이라고 보장하는 데이터도 아니다.

## 파일을 읽는 순서

1. `scenario_summary.csv`: 사례 수와 실제 행 수.
2. 각 폴더의 `cases.csv`: 사례 ID, 대응 정상 사례, 시간 범위, 대상, 실제 행 수.
3. `processes.csv`: 모델에 입력할 14개 Process 컬럼만 포함.
4. `process_labels.csv`: 복합 PK로 연결하는 행별 정답·원본 출처·변경 내용.
5. `events.csv`: 유형, 구간, 대상 선택자, 변경 이유와 주입 수치.
6. `windows.csv`와 `window_labels.csv`: 시간 구간 입력과 정답을 분리한 파일.
7. `normal_processes.csv`: 같은 사례에서 장애를 주입하지 않은 대응 정상 대조군.
8. `validation.json`: 내보낸 CSV를 실제 규칙으로 검사한 최종 결과.

각 폴더의 `transactions_context.csv`와 `normal_transactions_context.csv`는
Transaction–Process 관계 규칙 검증용이다. IF 학습 입력에 Transaction 행을 섞지 않는다.
`manifest.json`에는 난수 설정, 고정 정책 해시, 파일 해시, Adapter·기간별 사용량이 있다.

## 사례 연결 방법

Process 입력에 `case_id`, 시나리오 이름, 정답을 추가하지 않았다.
`process_labels.csv`에서 `(transactionId, processId, retryCount)`로 사례를 연결한다.
하나의 사례에는 정상 배경 행과 이상 행이 함께 있으므로, 전체 CSV의 모든 행을 이상으로 취급하지 않는다.

정상 대조군은 대응 관측 입력과 Transaction ID를 공유한다. 중단으로 관측 입력에 없는
Transaction ID는 `events.csv`의 `missing_transaction_ids`에 기록돼 있다.
폭주로 추가된 실행은 정상 대조군에 없다. 단일 사례는 제공한 `load_case`로 로드할 수 있다.
관측 입력과 대응 정상 입력은 서로 다른 실행 세계다. 두 입력을 같은 배치로 합치면
동일 PK가 중복되므로 따로 추론하고 결과에 사례·역할을 붙여 비교한다.

```python
import sys
from pathlib import Path
import pandas as pd

# 프로젝트 루트에서 실행
sys.path.insert(0, str(Path('code/evaluation_benchmark').resolve()))
from load_case import load_case

dataset = Path('data/evaluation/input_stop')
case_id = pd.read_csv(dataset / 'cases.csv').iloc[0]['case_id']
observed = load_case(dataset, case_id)
normal = load_case(dataset, case_id, normal=True)
```

**사례마다 시간 집계와 상태를 초기화한다.** 독립 사례들의 가상 날짜는 겹칠 수 있다.
모든 사례를 하나의 시간축으로 합치면 생성하지 않은 가짜 폭주가 생긴다.
CSV 저장 순서는 재생 순서가 아니다. `load_case`는 완료 로그의 `endTime` 순서로 반환한다.
실시간 재생에서는 완료 전 소요시간을 미리 사용하지 않는다. `windows.csv`의 소요시간 통계도
해당 구간 안에서 완료된 행만 사용한다. 시작 시각 기반 요청 수는 로그가 늦게 도착할 수 있으므로
실시간 구현에서는 늦은 로그 처리·윈도우 재계산 정책이 별도로 필요하다.

## 시나리오별 생성 원리

### 개별 지연과 업무 집단 내 지연

Adapter·Process ID·처리량 집단의 정상 P95보다 지연을 증가시킨다.
표본이 30개보다 적으면 Adapter·처리량, 그다음 Adapter 집단으로 확장한다.
여전히 근거가 부족하면 조건부 지연의 대상에서 제외한다.
기본셋은 조건부 P95와 고정 룰 상한 사이의 여유 공간을 weak/medium/strong으로 나눠 사용한다.
대응 정상 실행보다 시간이 실제로 증가하는지도 검사한다. 불가능한 후보는
최대 128회까지 고정 난수 규칙으로 다시 추출하며 사례 수나 규칙 기준을 낮추지 않는다.
단일 지연은 한 단계, 집단 지연은 해당 구간의 여러 실행에 적용한다.

### 컬럼 관계 이상

같은 Adapter에서 표본이 충분한 서로 다른 처리량 구간의 시간을 교차 조합한다.
Process ID가 처리량을 고정하는 경우가 있어 서로 다른 업무의 Process ID를 사용할 수 있다.
이 관계는 업무 계약 위반을 확정한 것이 아니라 **Adapter 내 조건부 통계 관계를 깨뜨린 합성 사례**다.
두 대상 Process ID와 참고 분포는 이벤트 근거에 명시한다.
`totalCount = successCount + errorCount`는 그대로 유지하고 시간만 바꾼다.

### 시간대 폭주

한적한 시간의 정상 재생에 완전한 실행 묶음을 추가한다.
기본셋은 정상 대비 2–5배를 목표로 pulse·sustained·two_pulses 형태를 사용한다.
정수 건수와 실행 시각 때문에 실제 배율은 다를 수 있으므로 이벤트에 실제 증가량과 배율을 기록한다.
개별 행의 시간·처리량은 정상 범위에 둔다. STATUS나 오류 건수를 키워 쉽게 탐지하게 만들지 않는다.
기본 폭주·중단 사례에서는 선택한 정상 실행 템플릿을 반복해 행 값의 변화를 통제하고
입력 빈도만 변경한다. 템플릿과 일정은 사례마다 바뀐다.

### 입력 중단

기본셋에서는 5·10·20분 동안 완전한 실행 묶음과 해당 관측 Transaction을 제거한다.
이때 이미 관측된 Transaction의 일부 단계만 삭제하지 않는다.
따라서 Process count 불일치로 중단을 탐지할 수 없으며, 과거 기대 입력과 현재 0건을 비교해야 한다.
원본 수집 공백을 장애로 추정하지 않고, **수집기가 정상이며 실행이 예상됐다는 합성 설정**을 명시한다.
누락된 사건은 행별 정답이 아니라 이벤트·시간 구간 정답에 존재한다.

### 점진적 악화

20·30·40분에 걸쳐 선형·계단형·smooth 변화로 시간을 늘린다.
기본 증가량은 집단 정상 중앙값의 30·60·100%를 목표로 하되 고정 규칙 상한을 넘지 않는 범위로 제한한다.
상한 여유는 집단 P75뿐 아니라 해당 사례의 실제 정상 최대 시간으로도 확인한다.
원래 실행 시간의 변동은 남겨 둔다. 매 행의 관측 시간이 완벽한 단조 증가라는 뜻이 아니라
**주입한 악화 성분이 누적 증가**한다는 뜻이다. 반올림으로 변화가 사라지지 않는지도 검사한다.

## 혼합 Hard의 의미

각 사례에는 6유형이 모두 들어 있다. 기본 90분 정상 재생 위에서 다음처럼 구간을 분리한다.

| 유형 | 기본 배치 | 어려워지는 이유 |
|---|---|---|
| 개별 지연 | 10–12분 | 조건부 P95 경계를 조금 넘어가지만 전체 범위에서는 자연스러운 시간 |
| 집단 지연 | 18–25분 | 작은 집단에서 함께 발생하는 경계 부근 지연 |
| 관계 이상 | 30–32분 | 개별 처리량·시간은 가능하지만 두 값의 조합이 어긋남 |
| 폭주 | 38–45분 | 작은 입력 증가, 짧은 집중 또는 반복 펄스 |
| 중단 | 50분부터 1–3분 | 다른 집단은 계속 동작하며 짧은 자연 공백과 구분이 어려움 |
| 악화 | 58–78분 | 정상 변동에 가려지는 작은 누적 지연 |

Hard 지연은 조건부 P95와 룰 상한 사이 여유의 2–12%를 사용한다.
폭주는 1.2–2배, 악화는 집단 중앙값의 5·10·20% 증가를 목표로 한다.
배경 실행은 다른 업무 집단에서 유지한다. 실행 ID에 유형·라벨을 넣지 않는다.

현재 IF가 놓친 사례를 골라 넣거나 IF 점수로 난이도를 조정하지 않는다.
Hard는 문맥과 관계를 봐야 하는 설계라는 뜻이며, 모든 모델에서 반드시 낮은 점수를 얻는다는 보장은 아니다.
6유형 중 하나만 맞힌 것을 전체 성공으로 보고하지 않는다.

## 하드룰 통과의 정확한 의미

기존 저장 모델에서 가져온 고정 정책을 사용한다. 테스트 데이터로 룰 분위수를 다시 맞추지 않는다.
각 metric·quantile에 Adapter 기준이 있으면 그 기준을 사용하고, 없으면 GLOBAL로 fallback한다.
Adapter 기준이 있는데도 무조건 더 작은 GLOBAL 기준을 적용하지 않는다.
P99와 P99.9 중 활성 기준을 모두 만족한다. 실제 비교 연산은 엄격한 `>`다.

- STATUS=S, 오류 건수=0, 정상 종료 시각.
- 처리·성공·오류·재시도 건수는 결측 없는 비음수 정수.
- 처리 건수 보존, SQL 필수값과 문자열 길이, 복합 PK 고유성.
- 종료가 시작보다 빠르지 않음, 의존 단계가 선행 단계 완료 후 시작.
- 원본 부모의 기대 Process count를 보존한 관계 검사.
- 고정 P99·P99.9와 추가 입력 품질 규칙 통과.

표본을 뽑은 뒤 전체 실행을 다시 조회한다. 정상 Transaction 문맥은 장애 주입 전에 확보한다.
관측 후 남은 행 수를 기대 개수로 덮어써서 검사를 통과시키지 않는다.
최종 검증은 실제 11개 룰의 탐지 0건과 미평가 0건을 요구한다.

## 데이터 출처와 다양성

원본 3개 기간의 Process 3,714,199행을 확인했고, 원본 Transaction까지 확인한
정상 실행 템플릿 13,314개와 21종 Adapter를 확보했다.
각 Adapter의 실제 사용량은 `adapter_source_coverage.csv`, 각 평가셋의 manifest에서 확인한다.
행은 S여도 전체 실행에 실패·불일치·룰 초과가 있으면 템플릿에서 제외한다.

표본은 기간·Adapter·처리량별 Transaction 해시 층화 표본이다. 실제 운영 빈도를 그대로 반영하는 표본이 아니다.
지연·관계 이상을 만들기 위한 표본이 부족한 Adapter는 배경·폭주·중단 등 가능한 유형에 사용한다.
각 유형에서 모든 Adapter가 이상 대상이 되는 것은 아니다.
기존 3개 전문가 모델 외 Adapter도 포함되므로 모델 평가 시 GLOBAL-only 경로가 생길 수 있다.

CSV는 기본 입력 형식을 유지하지만 Transaction ID와 실행 날짜는 합성이다.
Process ID·Adapter·채널·처리량·정상 시간은 원본 실행에서 재사용한다.
단계 간 순서는 보존하고 단계 간 간격은 합성 2–25ms로 재생한다.
전후 정상 변동과 원본 표본 선택을 바꿔 다양성을 만들며,
ID와 절대 날짜를 제거한 내용 해시로 동일한 복제 사례가 없는지 확인한다.

과거 입력 이력은 평가 날짜보다 앞선 14일의 **명시적인 합성 정상 이력**이다.
한적한 시간·주간·주말의 상대 패턴을 설정하고 요청 수를 작은 재생 규모로 제한한다.
원본 수집 공백을 0건으로 해석하거나 이 요청 수가 실제 서비스 부하라고 주장하지 않는다.

## 평가할 때 주의할 점

- 개별·집단 지연 및 관계 이상: 행별 Precision/Recall, PR-AUC 등을 시나리오별로 계산.
- 폭주·중단·악화: 사건 탐지율, 최초 탐지 지연, 구간 탐지 성능, 정상 대조군 오경보를 함께 계산.
- 중단은 0행 사건이다. 현재 행 단위 IF만으로 직접 평가할 수 없음. 주기적 윈도우·이력 피처가 필요.
- 초기 악화와 정상 시간 변동이 겹칠 수 있음. 모든 변경 행을 확정적으로 구별할 수 있다고 해석하지 않음.
- 이벤트 구간 안에서 한 번 탐지했다고 모든 행의 정답을 맞힌 것으로 바꾸는 point adjustment를 하지 않음.
- Hard는 유형별 성능과 6유형을 모두 탐지한 사례 비율을 별도로 제시.
- 정상 대조군·counterfactual 값·원본 출처·라벨·이벤트 이름은 모델 피처로 사용 금지.
- 이 데이터로 학습하거나 threshold를 튜닝한 뒤 동일 셋을 최종 평가로 재사용하지 않음.

원본 정상 패턴을 재사용하므로 기존 모델의 학습 원본과 겹칠 수 있다.
이 셋은 시나리오 스트레스 테스트용이며 독립 외부 데이터 성능이나 실제 장애 탐지 정확도의 증거와 구분한다.
