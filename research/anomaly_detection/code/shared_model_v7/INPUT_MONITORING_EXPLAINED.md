# 완료 로그 즉시 판정과 입력 공백 감시

## 사용자가 설명한 입력

트랜잭션이 완료되면 그 실행에 속한 Process 로그와 컬럼 값을 받는다. 모델은 이 Process 정보로 소요시간과 처리 건수 등을 계산한다. Transaction 완료를 기다리는 상위 서비스의 전달 방식과, 모델이 Transaction 테이블을 추가 입력으로 요구하는지는 별개다.

## 즉시 판정과 1분 집계는 같은 개념이 아니다

- 완료 로그 한 건의 `endTime - startTime`, 처리 건수 대비 지연은 그 로그를 받은 즉시 계산할 수 있다.
- 1분 집계는 같은 Adapter + Process의 실행들을 60초짜리 구간으로 묶어 실행 수, 최대 소요시간, 평균 잔차 등을 만드는 것이다. 예: 10:00:00~10:00:59 사이 실행 4건을 1행으로 요약한다.
- 통계의 관측 구간 길이와 점수 계산 주기는 별개다. 일반적으로 최근 60초 통계를 이벤트마다 갱신할 수 있으므로, 60초를 본다는 사실만으로 매번 60초 기다려야 하는 것은 아니다.
- **다만 현재 v7 전달물은 연속된 1분 격자를 입력받는 분 단위 연구 모델이다.** `count_filter.Context.groups`, `rank_context.Context.transform`, cadence 파생 함수는 1분 간격을 검사한다. 5초 간격 행을 그대로 넣거나, 미완성 1분 카운트를 완성된 1분 통계처럼 넣으면 기존 학습·평가 조건과 달라진다.
- 따라서 완료 로그 즉시 판정이 원리상 가능하다는 설명과, 현재 전달물이 이미 이벤트 기반 수초 내 판정을 구현·검증했다는 주장은 구분해야 한다. 현재 코드/전달물의 입력 계약을 바꾸지 않았고, 운영 worker도 이번 분석에서 구현하지 않았다.
- 수초 지연은 최종 경보 시각에서 로그 수신 시각을 뺀 값과 실제 사건 시각에서 뺀 값을 각각 측정해야 한다. 트랜잭션 완료 전 지연은 완료 로그만으로는 관측할 수 없다.

## 입력 중단은 무엇을 비교하나

새 로그가 없으면 `on_log` 콜백도 실행되지 않는다. 입력 공백은 별도 타이머가 이미 알려진 활성 Adapter + Process를 확인해야 한다. 새 Process 로그를 만들어 넣는 것이 아니라 **실행 수 0인 감시 기록**을 생성한다.

현재 코드의 주요 신호:

| 신호 | 계산과 의미 |
|---|---|
| `gap_expected_prefix` | `log(1 + 연속 0건 분 수 × 초기 최대 8분 관측의 평균 분당 실행 수)`; 초기 관측은 정상임이 보장되지 않음 |
| `gap_expected_recent` | `log(1 + 연속 0건 분 수 × 직전 최대 15분 평균 실행 수)` |
| `traffic_zero_logprob` | 같은 요일 유형·시간대 정상 참조에서 0건일 확률을 p라고 할 때 연속 0건마다 `-log(p)` 누적, 최대 20; 실행이 있으면 초기화 |

세 신호가 학습 코어 입력과 경보 보정에 사용되고, 최종 정규화 점수가 1을 초과하면 경보다. ‘몇 분 없으면 무조건 장애’라는 고정 하드 룰과는 다르다. 최근 평균은 긴 중단이 지속되면 낮아질 수 있으므로 세 신호를 구분해서 해석한다.

예시(설명을 위한 가상 수치): 평소 거의 매분 실행되며 정상 참조에서 0건일 확률이 0.1인 집단이 3분 연속 0건이면 누적 공백 신호는 약 `3 × -log(0.1) = 6.91`이다. 평소 0건일 확률이 0.9인 집단에서는 같은 3분 공백도 약 0.32다. **이 값은 최종 이상 점수나 장애 확률이 아니며, 이 예시만으로 경보 여부를 확정할 수 없다.**

## 완료 시점에만 받는 환경에서의 한계

- 이 입력만으로 직접 확인하는 것은 **완료 로그가 오지 않는 현상**이다. 실제 요청이 줄었는지, 작업이 진행 중인지, 트랜잭션이 오래 걸리는지, 로그 전달/수집이 지연되는지는 구분할 수 없다.
- 기존 실험의 `native_execution_arrivals`는 실행 시작 기준 분당 개수다. 완료 후에만 모든 로그가 공개되는 운영 환경에서는 진행 중 실행의 시작 개수를 실시간으로 알 수 없다. 시작 기준 실행 수가 실시간 입력된다고 가정해서는 안 된다.
- 운영에서는 수신/완료 기준 빈도와 정상 이력을 같은 기준으로 다시 구성·검증하거나, 실행 시작 이벤트/진행 상태를 추가로 받아야 한다. 단순히 기존 시작 기준 통계에 완료 도착 건수를 대신 넣으면 분포가 달라질 수 있다.
- 업무 실행 시간표, 활성/비활성 정보, 수집기 heartbeat, 실행 시작 이벤트가 있으면 ‘작업 미실행’과 ‘로그 수집 중단’을 더 잘 구분할 수 있다. 이 추가 입력이 현재 모델에 이미 구현됐다는 뜻은 아니다.

발표 답변: **“완료 로그의 지연은 도착 즉시 계산할 수 있습니다. 반면 입력 중단은 새 로그가 없으므로 별도 타이머가 공백을 확인하고, 해당 집단에서 평소 얼마나 자주 로그가 왔는지와 비교합니다. 완료 로그만으로는 작업 중단과 수집 지연을 확정 구분할 수 없습니다.”**
