### 모델별 역할은 지금 얼마나 구분되나?
- **K-means — 범용 탐지 후보:** 개별 지연 **62.63%**, 시간대 폭주 **62.94%**로 두 유형에서 다른 모델보다 뚜렷하게 높다. 집단 지연·입력 중단도 비교적 안정적이다.
- **LOF — 지속되는 지연·중단의 보완 후보:** 집단 지연 **87.43%**, 입력 중단 **83.41%**, 점진적 악화 **75.57%**로 F1이 상대적으로 높다. 일부 차이는 작으며, 시간대 폭주 **3.16%**는 매우 취약하다.
- **IF — 차별화 재설계 필요:** 집단 지연 **82.27%** 등 일부 유형은 잘 찾지만, 개별 지연 **0%**라 현재 결과를 두고 “개별 지연 전문가”라고 설명하면 틀리다. Hard F1이 세 모델 중 가장 높은 **34.22%**여도 절대 성능이 낮아 독보적인 강점으로 포장하지 않는다.

- **해석 범위:** 피처 구성·전처리·경보선도 서로 다르므로 이 차이를 알고리즘 자체의 보편적 특성으로 단정하지 않는다. 시간 변화는 모델이 저절로 이해하는 것이 아니라 우리가 만든 과거 기반 수치 피처로 전달한다.
### 무엇을 보고 판단하나?
- **실행 종류:** `adapterType + processId`. 실제 업무 의미를 나타내는 별도의 ‘업무’ 컬럼은 아니다.
- **처리 건수:** `totalCount`. 실행 한 건이 처리한 레코드 수이며, 분당 실행 횟수와 다르다.
- **소요시간:** `endTime - startTime`. 기존 실행 종류·처리 건수별 참조의 이탈 정도 및 과거 완료 관측 대비 변화를 수치화한다.
- **초기 비교 기준:** 해당 스트림의 초기 완료 관측 최대 **6개**. ‘6분’이 아니며 정상이라고 보증된 구간도 아니다. 처음부터 느린 관측이 섞이면 기준이 오염될 수 있다.
- **실시간 방향:** 현재 시각까지 시작·완료된 로그와 과거 이력만 사용한다. 미래 구간을 모아서 과거를 다시 판정하지 않는다. 빈 분 생성·이력 보관·지연 도착 처리는 worker 구현이 필요하다.

### 무엇으로 학습했나?
- 원본 3개 수집 기간에서 **STATUS=S이고 하드 룰을 통과한 정상 후보 실행**을 고르고, 별도의 정상 후보 스트림을 재생해 학습했다. 원본 전체를 그대로 넣은 것은 아니다.
- 학습 자료는 정상 후보 **19,793개 1분 집계**, 정상 점수 보정 자료는 별도 **17,925개**. LOF는 중복 제거 후 최대 **4,096개 참조점**을 사용한다.
- **S는 처리 성공이지 성능 정상 보장이 아니다.** 알고리즘은 정상 후보로 학습했지만 피처·하이퍼파라미터 선택에는 개발용 정답을 활용했다.
### 현재 구조 — Adapter 전문가와 앙상블은 사용하지 않음
- IF·K-means·LOF **각각 하나의 전체 단일 모델**이다. 세 알고리즘을 합친 앙상블도 아니다.
- **IF·LOF:** Adapter 파생 수치 9개를 직접 포함한 총 **28개 피처**.
- **K-means:** 개발 검증에서 더 나았던 총 **19개 간결 피처**. Adapter 파생 수치 9개를 직접 넣지는 않지만 `current_source_upper/lower` 등 기존 집단 참조 정보는 간접 활용한다.
- Adapter별 **정상 참조 통계**와 Adapter별 **별도 학습 모델**은 다르다. 현재는 전자를 활용하며 후자의 전문가 모델은 없다.

### 성능표와 경보선 읽는 법
- **Precision:** 경보 중 실제 이상 비율. **Recall:** 실제 이상 중 탐지한 비율. **F1:** 두 지표를 함께 보는 점수.
- **Accuracy:** 전체 판단 중 정답 비율. 전부 정상이라고 해도 **82.39%**이므로 이것만 보지 않는다.
- **Threshold:** 보정된 이상 점수가 경보선을 **초과**하면 경보한다. 점수는 장애 확률이 아니며 모델 간 절댓값을 비교하지 않는다.
- **P99.25/P99.5:** 별도 정상 calibration 점수의 분위수 기준이다. 실제 새 환경의 오탐률이 정확히 0.75%/0.5%가 된다는 보장은 아니다.

	### 분석
	**탐지 방식:** 정상 후보 피처를 무작위 분할로 나눌 때 상대적으로 쉽게 분리되는 관측에 높은 이상 점수를 준다.

	1. **전체 결과**
		- Accuracy **89.67%**, Precision **81.90%**, Recall **53.06%**, F1 **64.40%**.

	2. **우리 task에서 잘 찾는 쪽**
		- 집단 지연 F1 **82.27%**, 입력 중단 **73.07%**, 점진적 악화 **69.35%**.
		- 이 세 유형에서도 K-means·LOF보다 우세하지는 않아 IF만의 전문가 역할로 확정할 근거는 부족하다.
	3. **반드시 남겨야 할 약점**
		- 개별 지연은 실제 이상 분 **5,093개 중 TP 0개**, 컬럼 관계도 **TP 0개**. 개별 지연이 해결됐다고 해석하면 안 된다.
		- 시간대 폭주 **34.00%**, Hard **34.22%**. Hard는 상대 1위여도 절대 성능이 낮다.
	**실제 설정:** 28개 피처, trees **300**, max_samples **1024**, asinh 변환. 관측 상태별 정상 점수 robust 보정 후 정상 calibration **P99.25**를 경보 기준으로 사용.

	**현재 역할:** 세 모델 중 가장 범용적인 탐지 후보. 특히 개별 지연·시간대 폭주에서 상대적으로 뚜렷한 차이가 있다.

		- 컬럼 관계 **9.03%**, Hard **31.25%**. 가장 범용적이라는 말이 모든 이상 유형을 잘 찾는다는 뜻은 아니다.

	### 무엇을 보고 판단하나?
	- **실행 종류:** `adapterType + processId` 조합. 별도의 ‘업무’ 컬럼이나 실제 업무 의미를 뜻하지 않는다.
	- **처리 건수:** `totalCount`. 한 실행에서 처리한 건수이며, 일정 시간의 실행 횟수와는 다르다.
	- **소요시간:** `endTime - startTime`. 같은 실행 종류·처리 건수의 과거 분포에서 얼마나 벗어나는지 피처로 만든다. 참고 사례가 부족하면 더 넓은 집단을 사용한다.
	- **시간 변화:** 1분마다 실행 횟수와 소요시간을 집계하고, 최근 수준·증가 추세 등을 숫자로 만든다. 세 모델 모두 이런 피처를 보며, 시간 흐름을 저절로 이해하는 모델은 아니다.
	- **입력:** Process 로그 기반 피처. Transaction은 모델 입력이 아니라 생성·하드 룰 검증의 보조 정보다.
	### 무엇으로 학습했나?
	- 원본 중 **STATUS=S이고 하드 룰을 통과한 정상 후보 실행**을 골라, 이를 재생한 정상 후보 스트림으로 학습·보정했다. 원본 전체를 그대로 학습한 것은 아니다.
	- **S는 처리 성공이지 정상 성능 보장이 아니다.** 지연 등이 섞여 있을 수 있어, 모델은 ‘정상으로 가정한 과거 패턴과 다른가’를 판단한다.
	- 알고리즘 학습은 비지도 방식이지만, 피처·설정·경보 기준 선택에는 개발용 정답을 활용했다.
	### 전체·Adapter·앙상블의 차이
	1. **전체 모델:** 여러 Adapter의 데이터를 함께 학습한 공통 모델.
	2. **Adapter 모델:** 해당 Adapter 데이터로 별도 학습한 모델. 현재 지원은 DB.READER, DB.WRITER, FILE.READER, FILE.WRITER, SERVICE.EXECUTOR의 5종이다. 미지원·신규 Adapter는 전체 모델을 사용한다.
	3. **앙상블:** 같은 알고리즘 안에서 전체와 Adapter 점수를 보정해 현재 가중치 **0.9 : 0.1**로 결합한다. IF·K-means·LOF 세 알고리즘을 합친 것은 아니다.
	- Adapter 표에는 미지원 Adapter의 전체 모델 대체 결과도 포함된다. 이번 평가에서 대체 구간은 약 49.44%이므로, 표 전체를 순수 Adapter 모델 성능으로 읽으면 안 된다.
	### 성능표 읽는 법
	- **Precision:** 경보 중 실제 이상 비율. **Recall:** 실제 이상 중 찾아낸 비율. **F1:** 두 지표를 함께 보는 점수. **정상 오탐률:** 정상인데 경보한 비율.
	- **Accuracy:** 전체 판단 중 맞춘 비율. 정상 구간이 많아 전부 정상으로 판단해도 82.39%이므로 Accuracy만 보지 않는다.
	- **Threshold:** 이상 점수가 이 경보 기준을 넘으면 탐지한다. 정상 후보 점수로 보정한 기준이며, 이를 넘었다고 실제 장애가 확정되는 것은 아니다.
	<callout icon="📌" color="blue_bg">
		**표의 범위:** 최종 후보 v18 · mild-v2 평가셋 · 1분 단위 판단 결과. 아래 이미지는 기존 6개 시나리오와 Hard를 모두 포함한다. 설명은 핵심 5개 시나리오 중심으로 줄였으며, 두 유형을 제외해 다시 계산한 성능표가 아니다.
		**해석 한계:** 합성 데이터의 연구 결과이며 운영 성능은 미확인이다. 현재 점수에는 모델 개선과 평가셋 난도 완화 효과가 함께 포함된다. 세부 비교는 첨부 보고서에서 확인할 수 있다.

	## 1.  Isolation Forest {toggle="true"}
		### **전체적 성능 표**
		---
		![](notion-file-block://e67efae6-05c2-4229-9786-c4902af5612e/0f0a3644-7f89-4888-98c9-434bd407d3a5?space_id=b2cd544f-33e0-4dce-9441-6b075f177218&name=if_performance.png)
		### 분석
		---
		**탐지 방식:** 피처와 기준값을 무작위로 골라 데이터를 반복해서 나눈다. 다른 사례들과 달라 적은 분할만으로 혼자 분리되는 데이터에 높은 이상 점수를 준다.
		**한 줄 특징:** 정상 후보 패턴에서 튀는 개별 실행을 찾는 데 상대적으로 강했다.
		1. **전체 모델**
			- 개별 지연 F1 **86.18%**, 입력 중단 **77.99%**. Precision **74.05%**로 IF 안에서는 경보 정확도가 가장 높았다.
			- 점진적 악화 F1 **20.04%**로, 작은 변화가 누적되는 상황은 많이 놓쳤다.
		2. **Adapter 모델**
			- 정상 오탐률 **1.72%**로 낮지만 종합 F1 **30.99%**로 전체 모델 **45.39%**보다 낮았다. 경보가 적다고 탐지를 잘하는 것은 아니다.
			- 지원 Adapter 구간만 보면 전문가 F1 **4.96%**, 같은 구간의 전체 모델은 **37.96%**다. 현재 결과는 Adapter 전문가 자체가 유리하다는 근거가 아니다.
		3. **앙상블 모델**
			- 종합 F1 **47.78%**로 현재 9개 구성 중 가장 높았다. 다만 Recall **35.65%**로 놓치는 이상이 여전히 많다.
			- 정상 오탐률 **2.90%**로 전체 모델 **2.45%**보다 높다. 결합·경보 기준 보정을 함께 바꾼 결과여서 전문가만의 기여는 분리해 입증하지 않았다.
	## 2. Clustering {toggle="true"}

		### 분석
		---
		**탐지 방식:** MiniBatch K-means로 정상 후보의 비슷한 피처 패턴을 여러 그룹으로 묶는다. 새 데이터가 가장 가까운 그룹 중심에서 얼마나 벗어났는지 점수로 만든다.
		**한 줄 특징:** 일정 구간의 집단 지연·입력 중단에서 상대적으로 강했다. 여러 로그를 저절로 읽는 것이 아니라 시간 집계 피처를 활용한 결과다.
		1. **전체 모델**
			- 집단 지연 F1 **62.04%**, 입력 중단 **82.20%**로 세 알고리즘의 전체 모델 중 가장 높았다.
			- 점진적 악화 F1 **3.94%**로 약했다. 조금씩 변하는 패턴을 충분히 구분하지 못한 결과다.
		2. **Adapter 모델**
			- 종합 F1 **40.84%**로 전체 모델 **44.20%**보다 낮았다.
			- 점진적 악화는 **10.88%**로 전체보다 높지만, 정상 오탐률은 **5.70%**로 전체 **3.75%**보다 높다. Adapter별 학습이 항상 개선으로 이어지지는 않았다.
		3. **앙상블 모델**
			- 종합 F1 **45.19%**, 입력 중단 **82.80%**. 입력 중단은 세 알고리즘의 앙상블 중 가장 높았다.
			- 점진적 악화는 **6.64%**로 여전히 낮고, 정상 오탐률 **4.39%**도 전체보다 높다.
	## 3. LoF {toggle="true"}

		![](notion-file-block://953bfdaf-7ddc-40f2-aa89-ca70c5755808/a1dfcfcf-c145-45ed-b9c8-2f4c7afbbc57?space_id=b2cd544f-33e0-4dce-9441-6b075f177218&name=lof_performance.png)

		---

		2. **Adapter 모델**
			- 시간대 폭주 F1 **35.65%**로 LOF 전체·앙상블보다 높았다.
			- 종합 F1 **37.53%**로 전체보다 낮았다. 지원 Adapter 구간만 비교해도 전문가 **25.30%**, 전체 **37.96%**로 전문가가 우세하지 않았다.
		3. **앙상블 모델**
			- 종합 F1 **43.86%**, 점진적 악화 **30.07%**. 점진적 악화는 세 알고리즘의 앙상블 중 가장 높았다.

# 벤치마크 데이터셋
<callout icon="🧪" color="gray_bg">
	**목적:** STATUS=S이고 하드 룰에도 걸리지 않는 지연·실행 빈도·추세 이상을 모델이 찾는지 비교한다.
	**생성:** GPT가 작성한 Python 코드로 기존 정상 후보 로그를 변형·재배치하고 이상을 주입했다. GPT가 실제 장애를 수집했거나 원본과 무관하게 모든 값을 만든 것은 아니다.
</callout>
- **재료:** 3개 수집 기간의 정상 후보 실행에서 Adapter·Process·처리 건수·소요시간을 가져오고, ID·재생 시점은 합성했다. 시간대별 평소 실행 횟수 역시 합성 이력이므로 실제 운영 빈도와 동일하다고 볼 수 없다.
- **정상 대조군:** 같은 조건에서 이상을 넣은 사례와 넣지 않은 사례를 함께 만들었다. 정상 배경도 포함돼 있어 모든 행이 이상은 아니다. 별도 정답으로 탐지와 오탐을 평가하며, 정답은 모델 피처로 쓰지 않는다.
- **규모:** 기존 6개 시나리오마다 이상 5,000개 + 정상 5,000개 사례, Hard는 각각 1,000개. 사례 수는 CSV 행 수·1분 판단 수와 다르다.
- **현재 평가:** 같은 기존 `mild-v2` 데이터의 **2,167,766개 1분 판정**(정상 1,785,918 / 이상 381,848). 이번 모델 개선에서는 데이터·정답·난이도·Hard를 변경하지 않고 세 단일 모델로 다시 평가했다.
- **읽는 순서:** 설명은 개별 지연·집단 지연·시간대 폭주·입력 중단·점진적 악화의 핵심 5개를 중심으로 읽는다. 컬럼 관계는 겹치는 보조 시험, Hard는 혼합 스트레스 시험으로 유지한다. **상단 성능표는 6개 시나리오와 Hard를 모두 포함한 재평가 결과**이며 두 유형을 뺀 수치가 아니다.
- **공통 조건:** 모든 STATUS=S, 하드 룰 적발·미확인 플래그 0건. 입력 중단은 행이 사라지는 이상이므로 빈 1분 구간도 평가한다. 채점 때 이상 구간 전체를 탐지한 것으로 부풀리는 point adjustment는 사용하지 않았다.
### 참고 연구
- [Schmidl et al., PVLDB 2022](https://timeeval.github.io/evaluation-paper/): 여러 이상 유형과 모델을 나누어 비교하는 평가 관점을 참고했다.
- [Kim et al., AAAI 2022](https://arxiv.org/abs/2109.05257): 탐지 성능 과대평가 문제를 참고해 point adjustment를 제외했다.
- [Tatbul et al., NeurIPS 2018](https://arxiv.org/abs/1803.03639): 시점과 구간 평가를 구분하는 관점을 참고했다. 세 논문의 데이터 생성기·평가 공식을 그대로 재현한 것은 아니다.
## 1. 개별 지연 {toggle="true"}
	### 목적
	같은 `adapterType + processId`·비슷한 `totalCount`의 평소 실행보다 **한 실행만 유독 느린 경우**를 탐지하는지 본다.
	### 생성 방식
	특정 Process 한 건의 소요시간을 늘린다. 자기 조건의 정상 후보 P95보다 길게 만들되 하드 룰 상한은 넘지 않게 하고, STATUS·건수·후속 단계의 시간 정합성은 유지한다.
	- **예시:** 평소 100ms인데 대부분은 그대로이고 한 실행만 1,000ms. 숫자는 이해를 돕는 예시이며 고정 생성값은 아니다.
## 2. 집단 지연 {toggle="true"}
	### 목적
	같은 `adapterType + processId`로 반복되는 **여러 실행이 일정 시간 전반적으로 느려지는 경우**를 본다. 다른 Process ID들이 동시에 느려져야 한다는 뜻은 아니다.
	### 생성 방식
	정상 배경 중 특정 구간에서 대상 종류의 여러 실행 소요시간을 늘린다. 실행 횟수를 늘리는 폭주와는 구분한다.
	- **예시:** 평소 각 100ms이던 실행들이 10분 동안 대체로 300ms. 숫자는 설명용이다.

## 4. 시간대 폭주 {toggle="true"}
	### 목적
	평소 실행이 적은 시간대에 **실행 횟수가 급증하는 경우**를 본다. 한 실행의 `totalCount`를 부풀리는 시험이 아니다.
	### 생성 방식
	합성 정상 이력에서 한적하도록 설정한 새벽 구간에 정상 형태의 실행을 복제·추가한다. 짧은 급증·지속·두 차례 급증 등 모양을 달리한다.
	- **예시:** 평소 분당 2번 실행되던 종류가 분당 20번 실행됨. 숫자는 설명용이며 평소 빈도는 실제 운영 관측치가 아닌 합성 기준이다.
## 5. 입력 중단 {toggle="true"}
	### 목적
	평소 실행이 들어와야 하는 종류에서 **일정 시간 로그가 끊기는 경우**를 본다.
	### 생성 방식
	정상 배경에서 7/14/27분 구간의 실행을 통째로 제거하고 빈 1분 구간을 남긴다. Process 중간 단계만 지우는 것이 아니라 관련 실행·Transaction 정보를 함께 제거해 건수 불일치를 만들지 않는다.
	- **주의:** 수집기가 정상이고 실행이 예정돼 있다는 가정이다. 실서비스에서는 스케줄·휴일·수집기 상태를 확인하지 않고 0건을 장애로 확정할 수 없다.
## 6. 점진적 악화 {toggle="true"}
	### 목적
	같은 종류·비슷한 처리 건수의 반복 실행이 **시간이 갈수록 조금씩 느려지는 경우**를 본다.
	### 생성 방식
	정상 배경의 20/30/40분 구간에 지연 증가량을 점차 더한다. 직선·계단·부드러운 곡선 형태를 섞는다.
	- **예시:** 평균적인 수준이 100 → 120 → 150 → 190ms로 악화. 원래 실행별 변동도 남아 있어 모든 행의 시간이 반드시 순서대로 증가하는 것은 아니다.
	- **집단 지연과의 차이:** 집단 지연은 여러 실행이 함께 느린 상태, 점진적 악화는 시간이 갈수록 더 느려지는 변화에 초점을 둔다.
## 7. 혼합 Hard {toggle="true"}
	### 목적
	정상과 차이가 작은 여러 이상이 섞였을 때의 한계를 확인하는 **추가 스트레스 시험**이다.
	### 생성 방식
	90분 사례의 서로 다른 구간에 6개 이상 유형을 차례로 넣는다. 짧은 중단·약한 폭주·작은 지연 등으로 구분을 어렵게 만들었다. 모든 이상을 한순간에 넣는 것은 아니다.
	- 정상 대조군과 Hard는 최근 난도 완화 때 변경하지 않았다. Hard의 낮은 점수를 실제 장애 전체의 성능으로 일반화하지 않는다.
