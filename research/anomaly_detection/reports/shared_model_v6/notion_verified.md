최신 반영: <mention-date start="2026-10-18"/> · 근거: `shared_model_v6/release`
<callout icon="💡" color="gray_bg">
	**핵심: IF·K-means·LOF 모두 전체 Recall 60% 이상을 달성했다. 전체 Accuracy·Precision·F1은 이전 v5 이상이며, 모든 시나리오와 전체 정상 오탐률은 5% 미만이다.**
	**Recall 목표는 각 모델의 전체 합산 기준이다. 모든 시나리오에서 Recall 60% 이상이라는 뜻은 아니다.**
	현재는 **알고리즘마다 단일 전체 모델 1개**다. Adapter 전문가 모델·모델 간 앙상블은 사용하지 않는다. 이 페이지의 최신 수치는 **우리가 만든 5개 Process 시나리오** 결과이며 ADBench 결과가 아니다.

### 어떤 피처를 보고, 무엇을 바꿨나? {toggle="true"}
	- **실행 종류:** `adapterType + processId`. 별도의 ‘업무 의미’ 컬럼은 아니다.
	- **처리 건수:** `totalCount`. 실행 한 건이 처리한 레코드 수다. 분당 실행 횟수와 다르다.
	- **소요시간:** `endTime − startTime`. 같은 실행 종류·처리 건수의 정상 후보 분포와 비교한다. 참조가 부족하면 더 넓은 집단으로 대체한다.
	- **시간 피처:** 최근 실행 횟수 증가, 0건 지속, 지연 지속·증가 추세. 현재 시각까지의 완료 로그와 과거 이력만 사용하고 미래 관측은 사용하지 않는다.
	- **새 IF·LOF:** 기존 숫자 피처 15개를 **한 번의 지연 / 지연 지속 / 지연 추세 / 실행 폭주 / 입력 중단**의 5개 신호군으로 정리했다. 정상 후보의 중앙값·P95 범위로 크기를 맞춘 뒤 모델용 숫자로 요약했다. 이 이름들은 관측 신호군이며 정답 시나리오로 모델을 나누는 것이 아니다.
	- **IF 입력:** 신호군별 최대값 중 가장 큰 **요약 숫자 1개**. 따라서 현재 IF가 15차원 피처 조합을 그대로 학습한다고 설명하면 틀리다.
	- **LOF 입력:** 5개 신호군의 최대·평균 10개와, 현재 지연·지속 지연의 동시 상승 1개로 **총 11개**.
	- **K-means 입력:** 기존 지연·실행 횟수·과거 순위·중단 신호 **19개**를 유지했다.
	- Adapter·Process는 비교 기준을 찾는 데 활용하지만, 별도 Adapter 전문가나 ID 자체를 학습하는 범주형 모델은 아니다. 신호군별 정상 점수 통계도 전문가 모델이 아니다.
	- 과거 참조가 부족한 초기 구간은 가용 상태를 표시하고 넓은 정상 참조로 대체한다. 초기 완료 관측 최대 6개를 활용하는 피처도 있지만 그 구간의 정상을 보증하지는 않는다.
### 학습·서비스·검증과 한계 {toggle="true"}
	- 원본 세 기간에서 STATUS=S이고 고정 하드 룰을 통과한 실행 등으로 정상 후보 스트림을 만들었다. **S는 처리 성공이지 성능 정상 보장이 아니다.**
	- 추정기 학습 후보 **19,793개 분**, 별도 정상 점수 보정 **17,925개 분**. LOF는 중복 제거·표본 선택 후 **4,096개 참조점**을 사용한다.
	- 모델은 각각 단일 추정기다. Process 로그를 바탕으로 실행 종류별 **연속된 1분 격자**를 만들며 로그가 없는 분도 필요하다. Transaction은 모델 피처가 아니라 생성·정합성 검증의 보조 정보다.
	- 전달용 파일: `reports/shared_model_v6/release/handoff/{if,kmeans,lof}_shared.joblib`와 `manifest.json`. 의존 `code/` 모듈 트리도 필요하다.
	- worker의 빈 1분 생성·과거 상태 유지·지연 도착 처리·실제 배포는 별도 작업이다. 운영 배포 완료가 아니다.
	- 저장된 검증 기록: **79개 테스트 통과**, 독립 TP·FP·FN·TN/지표 재계산, 원시 Process 입력, 저장·로드 점수 일치, 미지 Adapter 대체, 미래 로그가 과거 판정을 바꾸지 않는지 검사.
	- 데이터·정답·난이도·ADBench는 변경하지 않았다. 기존 하드 룰 검증은 파일 해시가 동일한 경우 승계했으며 새 전수 실행이라고 주장하지 않는다.
	- **중요한 평가 한계:** 개발 정답뿐 아니라 반복 사용한 연구 벤치마크의 일부 정답도 후보·경보 정책 선택에 활용했다. 현재 결과는 **외부 블라인드 테스트가 아니다.** 정상 분위수 경보선도 운영 오탐률을 보장하지 않는다.
	- 강점 차이는 정상·이상 대조를 묶은 사례 단위 bootstrap 300회로도 확인했다. 점진적 악화의 LOF−IF F1 차이 0.15%p의 95% 구간은 **−0.24\~+0.51%p**로 0을 포함한다. 이 구간이 모델 선택 편향이나 운영 일반화까지 보증하지는 않는다.
	- 이전의 task F1 최저 30%·중앙값 60% 조건도 유지한다. 하지만 모든 task Recall 60% 조건을 충족했다는 뜻은 아니다.

## 1. Isolation Forest {toggle="true"}
	### 전체적 성능 표
	![](notion-file-block://00e0e22c-a1ca-42e1-ab58-ce32d8120765/92eba934-dca9-4bdd-a928-5ae36e40375d?space_id=b2cd544f-33e0-4dce-9441-6b075f177218&name=v6_if_performance_20261018.png)
	### 분석
	**쉽게 말하면:** 정상 기준에서 가장 크게 튄 지연·폭주·중단 신호를 요약한 뒤, IF에서 쉽게 분리되는 관측을 이상 후보로 본다.
	- **강점:** 집단 지연 F1 **86.90%**, 입력 중단 **84.69%**. 전체 Recall **69.58%**, F1 **77.55%**.
	- **약점:** 개별 지연 Recall **35.79%**로 이상 분 5,093개 중 **1,823개만 탐지**했다. Precision은 98.65%지만 많이 놓치므로 탐지가 충분하다는 뜻은 아니다.
	- **주의:** 집단 지연 F1은 IF가 높지만 Recall만 보면 LOF **91.97%**가 IF **91.23%**보다 조금 높다. IF는 오탐이 더 낮아 F1에서 앞선다.
	- **실제 변경:** 15개 원천 숫자 → 정상 기준 정규화 → 가장 큰 신호 **1차원**. **400 trees / max_samples=64 / max_features=1.0 / seed=42**. 가장 큰 관측 신호군별 정상 점수 CDF 보정(alpha=0.5, 5개 참조군).
	- **현재 경보선:** 보정 이상 점수 **4.304303 초과**. 별도 정상 calibration 점수 P99.25 기반이다. 소요시간의 P99.25 하드 룰이 아니다.
	### 점수 분포와 경보선 {toggle="true"}
		일반 막대 히스토그램이다. 정상·이상 각각의 전체 판정 수를 분모로 비중을 표시한다. 점선 오른쪽이 경보이며, 표시 범위를 벗어난 꼬리도 지표에는 포함했다. 점수는 장애 확률이 아니고 모델 간 점수 절댓값을 비교하지 않는다.
		![](notion-file-block://86105eef-d4ee-47b5-a059-12ac293d3030/5e2a3904-8906-4395-9467-2351660d20f0?space_id=b2cd544f-33e0-4dce-9441-6b075f177218&name=v6_if_threshold_20261018.png)
## 2. MiniBatch K-means {toggle="true"}
	### 전체적 성능 표
	![](notion-file-block://e0e2d239-0764-41de-83dd-d9166225687a/efb5727b-0f8d-432a-b241-0960a062d483?space_id=b2cd544f-33e0-4dce-9441-6b075f177218&name=v6_kmeans_performance_20261018.png)
	### 분석
	**쉽게 말하면:** 정상 후보의 여러 패턴 중심을 만들고, 새 관측이 그 중심들과 얼마나 떨어졌는지 본다. 모든 중심에 대해 거리/정상 P95 반경을 계산하고 최솟값으로 점수를 만든다.
	- **강점:** 시간대 폭주 F1 **62.94%**로 가장 높고, 전체 정상 오탐 **1.73%**로 가장 낮다. 5개 시나리오 F1이 모두 62.63% 이상이다.
	- **약점:** 개별 지연 Recall **46.46%**, 시간대 폭주 **50.27%**. 상대적으로 가장 잘하는 폭주도 절반 정도는 놓친다.
	- **채택 이유:** 새 후보가 전체 F1을 약 0.98%p 높였지만 폭주 F1을 8.65%p 낮춰 탈락했다. **기존 모델을 그대로 유지했으며 새 성능 향상이라고 주장하지 않는다.**
	- **실제 설정:** **19개 피처 / 8개 군집 / n_init=10 / batch_size=2048 / max_iter=200 / seed=42**. 정상 공분산 whitening, 정상 P95 군집 반경, 관측 가능 상태별 정상 점수 CDF 보정.
	- **현재 경보선:** 보정 이상 점수 **5.854851 초과**. 별도 정상 calibration 점수 P99.75 기반이다.
	### 점수 분포와 경보선 {toggle="true"}
		점선 오른쪽이 경보다. 정상·이상 각각의 전체 판정 수를 분모로 비중을 표시했고, 표시 밖 꼬리도 지표에는 포함했다. 점수는 IF·LOF와 단위가 다르다.

	### 무엇을 보고 판단하나?
	- **실행 종류:** `adapterType + processId` 조합. 별도의 ‘업무’ 컬럼이나 실제 업무 의미를 뜻하지 않는다.
	- **처리 건수:** `totalCount`. 한 실행에서 처리한 건수이며, 일정 시간의 실행 횟수와는 다르다.
	- **소요시간:** `endTime - startTime`. 같은 실행 종류·처리 건수의 과거 분포에서 얼마나 벗어나는지 피처로 만든다. 참고 사례가 부족하면 더 넓은 집단을 사용한다.
	- **시간 변화:** 1분마다 실행 횟수와 소요시간을 집계하고, 최근 수준·증가 추세 등을 숫자로 만든다. 세 모델 모두 이런 피처를 보며, 시간 흐름을 저절로 이해하는 모델은 아니다.
	- **입력:** Process 로그 기반 피처. Transaction은 모델 입력이 아니라 생성·하드 룰 검증의 보조 정보다.
	### 무엇으로 학습했나?
	- 원본 중 **STATUS=S이고 하드 룰을 통과한 정상 후보 실행**을 골라, 이를 재생한 정상 후보 스트림으로 학습·보정했다. 원본 전체를 그대로 학습한 것은 아니다.
	- **S는 처리 성공이지 정상 성능 보장이 아니다.** 지연 등이 섞여 있을 수 있어, 모델은 ‘정상으로 가정한 과거 패턴과 다른가’를 판단한다.
	- 알고리즘 학습은 비지도 방식이지만, 피처·설정·경보 기준 선택에는 개발용 정답을 활용했다.
	### 전체·Adapter·앙상블의 차이
	1. **전체 모델:** 여러 Adapter의 데이터를 함께 학습한 공통 모델.
	2. **Adapter 모델:** 해당 Adapter 데이터로 별도 학습한 모델. 현재 지원은 DB.READER, DB.WRITER, FILE.READER, FILE.WRITER, SERVICE.EXECUTOR의 5종이다. 미지원·신규 Adapter는 전체 모델을 사용한다.
	3. **앙상블:** 같은 알고리즘 안에서 전체와 Adapter 점수를 보정해 현재 가중치 **0.9 : 0.1**로 결합한다. IF·K-means·LOF 세 알고리즘을 합친 것은 아니다.
	- Adapter 표에는 미지원 Adapter의 전체 모델 대체 결과도 포함된다. 이번 평가에서 대체 구간은 약 49.44%이므로, 표 전체를 순수 Adapter 모델 성능으로 읽으면 안 된다.
	### 성능표 읽는 법
	- **Precision:** 경보 중 실제 이상 비율. **Recall:** 실제 이상 중 찾아낸 비율. **F1:** 두 지표를 함께 보는 점수. **정상 오탐률:** 정상인데 경보한 비율.
	- **Accuracy:** 전체 판단 중 맞춘 비율. 정상 구간이 많아 전부 정상으로 판단해도 82.39%이므로 Accuracy만 보지 않는다.
	- **Threshold:** 이상 점수가 이 경보 기준을 넘으면 탐지한다. 정상 후보 점수로 보정한 기준이며, 이를 넘었다고 실제 장애가 확정되는 것은 아니다.
	<callout icon="📌" color="blue_bg">
		**표의 범위:** 최종 후보 v18 · mild-v2 평가셋 · 1분 단위 판단 결과. 아래 이미지는 기존 6개 시나리오와 Hard를 모두 포함한다. 설명은 핵심 5개 시나리오 중심으로 줄였으며, 두 유형을 제외해 다시 계산한 성능표가 아니다.
		**해석 한계:** 합성 데이터의 연구 결과이며 운영 성능은 미확인이다. 현재 점수에는 모델 개선과 평가셋 난도 완화 효과가 함께 포함된다. 세부 비교는 첨부 보고서에서 확인할 수 있다.
	</callout>

# 벤치마크 데이터셋
<callout icon="🧪" color="gray_bg">
	**목적:** STATUS=S이고 하드 룰에도 걸리지 않는 지연·실행 빈도·추세 이상을 모델이 찾는지 비교한다.
	**생성:** GPT가 작성한 Python 코드로 기존 정상 후보 로그를 변형·재배치하고 이상을 주입했다. GPT가 실제 장애를 수집했거나 원본과 무관하게 모든 값을 만든 것은 아니다.
</callout>
- **재료:** 3개 수집 기간의 정상 후보 실행에서 Adapter·Process·처리 건수·소요시간을 가져오고, ID·재생 시점은 합성했다. 시간대별 평소 실행 횟수 역시 합성 이력이므로 실제 운영 빈도와 동일하다고 볼 수 없다.
- **정상 대조군:** 같은 조건에서 이상을 넣은 사례와 넣지 않은 사례를 함께 만들었다. 정상 배경도 포함돼 있어 모든 행이 이상은 아니다. 별도 정답으로 탐지와 오탐을 평가하며, 정답은 모델 피처로 쓰지 않는다.
- **규모:** 현재 5개 task마다 이상 5,000개 + 정상 5,000개 사례. 사례 수는 CSV 행 수·1분 판단 수와 다르다.
- **현재 평가:** 남은 기존 `mild-v2` 5개 task의 **1,927,972개 1분 판정**(정상 1,596,121 / 이상 331,851). 남은 데이터·정답·난이도는 변경하지 않았다.
- **제외한 task:** 컬럼 관계·Hard 혼합은 사용자 요청으로 현재 평가·선정·지표에서 삭제했다. 원본은 `reports/retired_tasks_20261018`에 복구 가능하게 보관했다. ADBench는 변경하지 않았다.
- **공통 조건:** 모든 STATUS=S. 남은 CSV의 해시가 동일함을 확인한 뒤 기존 하드 룰 적발·미확인 플래그 0건 검증을 승계했다. 새 하드 룰 전수 실행이라고 주장하지 않는다. 입력 중단은 행이 사라지는 이상이므로 빈 1분 구간도 평가한다. 채점 때 이상 구간 전체를 탐지한 것으로 부풀리는 point adjustment는 사용하지 않았다.
### 참고 연구

- [Kim et al., AAAI 2022](https://arxiv.org/abs/2109.05257): 탐지 성능 과대평가 문제를 참고해 point adjustment를 제외했다.
- [Tatbul et al., NeurIPS 2018](https://arxiv.org/abs/1803.03639): 시점과 구간 평가를 구분하는 관점을 참고했다. 세 논문의 데이터 생성기·평가 공식을 그대로 재현한 것은 아니다.
## 1. 개별 지연 {toggle="true"}
	### 목적
	같은 `adapterType + processId`·비슷한 `totalCount`의 평소 실행보다 **한 실행만 유독 느린 경우**를 탐지하는지 본다.
	### 생성 방식
	특정 Process 한 건의 소요시간을 늘린다. 자기 조건의 정상 후보 P95보다 길게 만들되 하드 룰 상한은 넘지 않게 하고, STATUS·건수·후속 단계의 시간 정합성은 유지한다.
	- **예시:** 평소 100ms인데 대부분은 그대로이고 한 실행만 1,000ms. 숫자는 이해를 돕는 예시이며 고정 생성값은 아니다.
## 2. 집단 지연 {toggle="true"}
	### 목적
	같은 `adapterType + processId`로 반복되는 **여러 실행이 일정 시간 전반적으로 느려지는 경우**를 본다. 다른 Process ID들이 동시에 느려져야 한다는 뜻은 아니다.
	### 생성 방식
	정상 배경 중 특정 구간에서 대상 종류의 여러 실행 소요시간을 늘린다. 실행 횟수를 늘리는 폭주와는 구분한다.
	- **예시:** 평소 각 100ms이던 실행들이 10분 동안 대체로 300ms. 숫자는 설명용이다.
## 3. 시간대 폭주 {toggle="true"}
	### 목적
	평소 실행이 적은 시간대에 **실행 횟수가 급증하는 경우**를 본다. 한 실행의 `totalCount`를 부풀리는 시험이 아니다.
	### 생성 방식
	합성 정상 이력에서 한적하도록 설정한 새벽 구간에 정상 형태의 실행을 복제·추가한다. 짧은 급증·지속·두 차례 급증 등 모양을 달리한다.
	- **예시:** 평소 분당 2번 실행되던 종류가 분당 20번 실행됨. 숫자는 설명용이며 평소 빈도는 실제 운영 관측치가 아닌 합성 기준이다.
## 4. 입력 중단 {toggle="true"}
	### 목적
	평소 실행이 들어와야 하는 종류에서 **일정 시간 로그가 끊기는 경우**를 본다.
	### 생성 방식
	정상 배경에서 7/14/27분 구간의 실행을 통째로 제거하고 빈 1분 구간을 남긴다. Process 중간 단계만 지우는 것이 아니라 관련 실행·Transaction 정보를 함께 제거해 건수 불일치를 만들지 않는다.
	- **주의:** 수집기가 정상이고 실행이 예정돼 있다는 가정이다. 실서비스에서는 스케줄·휴일·수집기 상태를 확인하지 않고 0건을 장애로 확정할 수 없다.
## 5. 점진적 악화 {toggle="true"}
	### 목적
	같은 종류·비슷한 처리 건수의 반복 실행이 **시간이 갈수록 조금씩 느려지는 경우**를 본다.
	### 생성 방식
	정상 배경의 20/30/40분 구간에 지연 증가량을 점차 더한다. 직선·계단·부드러운 곡선 형태를 섞는다.
	- **예시:** 평균적인 수준이 100 → 120 → 150 → 190ms로 악화. 원래 실행별 변동도 남아 있어 모든 행의 시간이 반드시 순서대로 증가하는 것은 아니다.
	- **집단 지연과의 차이:** 집단 지연은 여러 실행이 함께 느린 상태, 점진적 악화는 시간이 갈수록 더 느려지는 변화에 초점을 둔다.
