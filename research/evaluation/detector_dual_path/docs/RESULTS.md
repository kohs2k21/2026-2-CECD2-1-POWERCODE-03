- 최초 탐지 P95: **탐지된 사건만** 집계; 경로별 탐지 집합이 달라 직접 속도 순위 비교 금지. 개별 사건의 탐지 지연은 JSON에 보존

## 실제 로컬 연산 부하

- 같은 선택 모델, 준비 10회·3회 교차 반복·각 경로 120작업·100Hz 강제 경합
- Python 실행 슬롯 2개·BLAS1·sklearn1; OS CPU 상한·전용 호스트 격리 없음
- 값: 3회 중앙값 [최소~최대], P95/P99는 제출→연산 완료 ms

- 추세 밀림: IF P95 171.958~499.166ms·최대518.817ms; KMeans P95 238.002~315.504ms·최대347.546ms
- 100Hz는 경합 시험 조건; 운영 추세 15/60초 일정과 구분
- 단독: 실시간 작업에 실행 슬롯 2개. 병행: 추세 루프가 대기 시간까지 슬롯 1개 점유, 실시간 슬롯 1개. 지연 차이는 슬롯 배분과 추가 부하가 함께 바뀐 결과
- 동일 실시간 슬롯·운영 추세 주기로 비교하지 않아 지연 증가를 ML 병행만의 비용이나 별도 컨테이너의 필요성으로 단정 금지
- RSS: 전체 실험 프로세스·실행 중 자식 포함, 컨테이너/모델별 비용 아님; 차이를 메모리 개선으로 해석 금지
- 성능 포함: 피처 schema 검사·raw_features·encoder 변환·모델 점수·로컬 대기. 제외: 원본 로그의 PROCESS prepare·시간창 집계·고객 API·PostgreSQL·큐·SSE. ESB 발생→판정 2~3초 SLA 미검증

## 추천·재현

- 두 입력 경로 분리를 구현 후보로 유지: 입력 중단 등 로그 부재의 감시에는 독립 타이머 필요. 추세의 Rule/ML 선택은 아직 미확정
- 실데이터 확보 전 운영 알고리즘·창/주기 확정 보류. 5분/60초를 공통 비교 기준으로 유지, 위 선택값은 합성 검증 후보
- 논리 Rule 병행·실제 API 공개 지연·피처 준비 포함 E2E 확인 후 운영 판단
- 한계: 단일 합성 인터페이스·시나리오당 3사건·좁은 시간대/요일·분할 간 달력 변화. 고객 성능 우열·통계적 유의성 근거 아님
- 정상 train은 1월 1일 목요일, threshold는 3월 2일 월요일, test는 5월 1일 금요일의 각 하루. train의 요일 값이 상수이므로 KMeans의 날짜 거리와 임계값 차이가 성능 해석에 섞일 가능성
- 폭주 주입: 도착 수 7배와 개별 totalCount 6배 동시 변경. 순수 유입량 변화에 대한 탐지 효과와 분리 불가
- 정상 감시 3.5시간·단일 seed: 0경보는 이번 표본의 관측값, 운영 오경보가 없다는 증거 아님
- 주평가: 사건·짝정상 경보/h. PROCESS 양성 정답 없는 폭주의 건수 변화는 PROCESS FP·사건 TP로 다르게 계산 가능
- 시간창 정답: 종료시점의 주입 활성 여부. 복구 뒤 남은 이상 이력 경보는 신규 사건 탐지로 미집계
- 검수 발견 후 중단 2회: 최종 시험·선택 결과 열람 전 정상시간 분모/재생 비용 수정; 완료 실행 이후 임계값·모델 재선정 없음
