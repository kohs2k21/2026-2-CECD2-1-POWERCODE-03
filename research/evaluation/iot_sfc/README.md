## 1. 목적과 확인 범위

ESB 로그 기반 시스템의 입력 경로를 IoT 데이터로 확장할 수 있는지 확인하기 위해,
IoT-SFC의 실제 연결 로그를 별도 어댑터로 읽고 새로운 Isolation Forest(IF)와 통계 규칙으로 판정했다.
판정 결과는 데이터셋의 정답 라벨과 비교했다.

이번 시험에서 확인한 것은 다음 세 가지다.

1. 민감 필드를 제외한 IoT 관측을 저장하고 PostgreSQL 큐를 통해 탐지할 수 있는가?
2. IoT 데이터로 학습한 IF와 통계 규칙이 실제 이상 판정을 생성하는가?
3. 그 판정이 제공된 정상·이상 라벨과 얼마나 일치하는가?

**관측 저장·큐 소비·실제 추론·라벨 비교는 수행했다. 그러나 소량 샘플에서 판정 불가 비율과 미탐이 높았으므로,
탐지 품질이 충분하거나 IoT 전체 환경에 일반화된다고 결론 내릴 수는 없다.**

기존 ESB용 학습 모델을 재사용한 시험이 아니다. 이번 샘플로 IF를 새로 학습했다.
파생변수 생성 모델, Rule 추천 모델, 서비스의 Rule CRUD, 학습 작업 큐, 운영 승인·적용,
기존 화면·알림은 이 시험 경로에 연결하지 않았다.

공식 train/test 분할을 사용한 결과가 아니다.

### 2.2 소량 표본 확보 방법

전체 ZIP을 받지 않고 HTTP Range 요청으로 **앞부분 1,048,576 bytes(1 MiB)**만 내려받았다.
서버의 `206 Partial Content` 응답을 확인하고, ZIP 첫 CSV 항목에서 완전하게 읽을 수 있는 행을 판독했다.
그중 `log_type=conn`인 앞쪽 20,000행을 선택했다.

선택한 행을 허용 필드 목록으로 투영한 후에만 샘플 CSV와 학습용 파일을 생성했다.
샘플 구성은 무작위 추출·공격별 균등 추출·전체 기간 층화 추출이 아니다.

| 샘플 항목 | 건수 또는 범위 |
|---|---:|
| 선택한 연결 관측 | 20,000 |
| 정상 라벨 | 10,620, 53.10% |
| 이상 라벨 | 9,380, 46.90% |
| 수치 피처를 모두 계산할 수 있는 관측 | 11,158, 55.79% |
| 수치 피처를 모두 계산할 수 없는 관측 | 8,842, 44.21% |
| 원천 시각 시작, KST | 2025-04-06 23:33:35.462984+09:00 |
| 원천 시각 종료, KST | 2025-04-07 23:32:05.518323+09:00 |

원천 시각을 UTC로 표현하면 2025-04-06 14:33:35.462984부터 2025-04-07 14:32:05.518323까지다.
관측 시각은 Zeek의 Unix 초 필드 `ts`를 해석했고, 십진수 원문도 보존했다.

**이 표본은 전체 데이터셋의 대표 표본이 아니다.** ZIP 전체 CRC 및 공식 전체 파일 SHA256 검증은 수행하지 않았다.
부분 다운로드로 생성한 샘플과 실제 사용한 모델·입력 파일의 무결성 검증을 구분해야 한다.

### 2.3 정답 라벨의 사용

| 필드 | 사용 방식 |
|---|---|
| `attack=0` | 정상 정답. 학습·보정 구간에서는 정상 기준선 선별에 사용 |
| `attack=1` | 이상 정답. 시험 판정과 비교 |
| `type_of_attack` | 평가용 부가 정보로 보존. 모델 입력 및 이번 이진 지표 계산에는 사용하지 않음 |

정답을 별도 `labels.jsonl`과 DB의 `ground_truth` 표에 보관했다.
Detector는 정답 표를 읽지 않고 관측 수치만 읽는다. 시험 구간 정답으로 피처·모델·임계값을 선택하거나 조정하지 않았다.
정상 학습 표본을 라벨로 선별했으므로, 라벨을 전혀 사용하지 않는 학습 조건으로 해석해서는 안 된다.

이번 검증은 **제공된 라벨과 판정의 일치도**를 평가했다. 제공자가 만든 라벨 자체의 정확성을 독립적으로 재검증한 것은 아니다.

## 3. 서비스 입력 매핑과 피처

### 3.1 ESB와 구분한 IoT 입력

| 원천 필드 | 시험 경로에서의 의미 |
|---|---|
| `ts` | 원천 관측 시각, Unix 초 |
| `uid` | 네트워크 연결 식별자 |
| `proto`, `service`, `conn_state`, `log_type` | 연결·프로토콜 메타데이터 |
| `duration` | 연결 지속 시간, 초 |
| `orig_bytes`, `resp_bytes` | 연결 방향별 바이트 수 |
| `orig_pkts`, `resp_pkts` | 연결 방향별 패킷 수 |

`uid`를 ESB의 `TRANSACTION_ID` 또는 Process 실행 ID로 바꾸지 않았다.
`duration`도 개별 업무 단계의 처리 시간으로 해석하지 않았다.
기존 T/P/M 표 대신 별도 `powercode_iot` 스키마를 사용했다.

### 3.2 모델 입력 일곱 개

고정된 수치 일곱 개를 다음 순서로 계산했다. `log1p(x)`는 자연로그 `ln(1+x)`다.

| 순서 | 피처 이름 | 계산 |
|---:|---|---|
| 1 | `log1p_duration` | `ln(1 + duration)` |
| 2 | `log1p_orig_bytes` | `ln(1 + orig_bytes)` |
| 3 | `log1p_resp_bytes` | `ln(1 + resp_bytes)` |
| 4 | `log1p_orig_pkts` | `ln(1 + orig_pkts)` |
| 5 | `log1p_resp_pkts` | `ln(1 + resp_pkts)` |
| 6 | `log1p_total_bytes` | `ln(1 + orig_bytes + resp_bytes)` |
| 7 | `log1p_total_pkts` | `ln(1 + orig_pkts + resp_pkts)` |

IF 입력에는 이 일곱 개만 전달했다. ID·원천 시각·정답 라벨·공격 유형·자유문은 입력하지 않았다.
기존 파생변수 생성 모델이 선택한 피처가 아니라, 이번 시험을 위해 고정한 수치 피처다.

### 3.3 저장 제외 및 결측 처리

BODY·payload, 계정·비밀번호, MQTT 인증값, IP, topic, URI, 자유문 등은 투영 허용 목록에서 제외했다.
제외 값은 관측 JSON·학습 파일·진단 출력·내용 hash에 포함하지 않았다.

필요 수치가 비어 있거나 `-`, 비유한 값, 음수, 잘못된 숫자인 경우 0으로 대체하지 않았다.
바이트·패킷 수에 소수 값이 있으면 사용할 수 없는 입력으로 처리했다.
일곱 피처를 모두 계산하지 못하면 Rule과 IF를 모두 수행하지 않고 `unavailable`을 기록했다.
따라서 일부 피처만으로 실행 가능한 규칙이 있더라도 이번 구현에서는 별도로 실행하지 않는다.

## 5. 학습·보정·시험 데이터 분리

### 5.1 분할 규칙

샘플의 서로 다른 `ts` 값을 십진수로 정렬한 후, 고유 시각 개수의 60%와 80% 위치를 경계로 고정했다.
행 수나 전체 시간 길이를 정확히 60:20:20으로 나눈 것은 아니다.

- 학습: 첫 경계보다 이전의 관측.
- 보정: 첫 경계 이상, 두 번째 경계 미만의 관측.
- 시험: 두 번째 경계 이상의 관측.
- 동일 uid가 여러 구간에 나타나면 해당 uid의 관측을 모두 제외한다. uid가 없는 행도 제외한다.

이번 번들에서는 uid 조건으로 제외된 행은 없었고, 세 구간의 행 수 합계는 20,000개다.
단, 같은 공격 세션 전체가 서로 다른 구간에 걸치지 않도록 하는 세션 단위 분리는 수행하지 않았다.

| 경계 | Unix 초 원문 | KST |
|---|---|---|
| 보정 시작 | `1744031797.900025` | 2025-04-07 22:16:37.900025+09:00 |
| 시험 시작 | `1744034102.478785` | 2025-04-07 22:55:02.478785+09:00 |

### 5.2 실제 구간별 건수

| 구간 | 전체 | 정상 | 이상 | 피처 완전 | 피처 불완전 | 피처가 완전한 정상 |
|---|---:|---:|---:|---:|---:|---:|
| 학습 | 12,283 | 6,030 | 6,253 | 7,548 | 4,735 | **3,042** |
| 보정 | 3,865 | 2,469 | 1,396 | 1,855 | 2,010 | **707** |
| 시험 | 3,852 | 2,121 | 1,731 | **1,755** | **2,097** | 599 |
| 합계 | 20,000 | 10,620 | 9,380 | 11,158 | 8,842 | 4,348 |

실제 모델 학습에는 학습 구간 12,283개 전체가 아니라 **정상·피처 완전 행 3,042개**를 사용했다.
임계값 산정에도 보정 구간의 **정상·피처 완전 행 707개**만 사용했다.
각 구간에 존재하는 이상 라벨 행을 정상 학습 표본에 넣지 않았다.

## 6. 모델과 Rule 구성

### 6.1 전처리와 Isolation Forest

먼저 `log1p` 피처를 계산하고, 정상 학습 3,042개만으로 `RobustScaler`를 학습했다.
보정·시험 구간에서는 학습한 scaler를 고정하여 사용했다.

| 항목 | 설정 |
|---|---|
| Scaler | `RobustScaler` |
| 중앙값 제거·스케일링 | `with_centering=True`, `with_scaling=True` |
| 분위수 범위 | 25%~75% |
| 단위 분산 강제 | `unit_variance=False` |
| 모델 | scikit-learn `IsolationForest` |
| 트리 수 | `n_estimators=100` |
| 트리당 표본 수 | `max_samples=256` |
| 입력 피처 비율 | `max_features=1.0` |
| 무작위 시드 | `random_state=42` |
| 병렬 작업 수 | `n_jobs=1` |
| 기타 | `contamination='auto'`, `bootstrap=False`, `warm_start=False` |

최종 이상 여부는 scikit-learn의 기본 `predict()` 결과를 그대로 사용하지 않았다.
다음 점수와 별도 보정 임계값을 사용했다.

```text
anomaly_score = -IsolationForest.score_samples(scaled_features)
IF 임계값 = 정상 보정 점수의 99번째 백분위수
IF 이상 = anomaly_score > IF 임계값
```

이번 번들의 IF 임계값은 **0.6433898044404835**다.
점수는 이상 확률이 아니며, 다른 모델의 점수와 같은 척도로 직접 비교할 수 없다.

### 6.2 통계 Rule

보정 구간 정상 표본에서 아래 세 피처의 99.5번째 백분위수를 각각 구하고,
하나라도 상한을 초과하면 Rule 이상으로 판정했다.

| 비교 피처 | 상한, log1p 변환 후 값 |
|---|---:|
| `log1p_duration` | 4.263686703962487 |
| `log1p_total_bytes` | 7.591861714889934 |
| `log1p_total_pkts` | 3.539984666946591 |

이 상한을 원래 단위의 초·바이트·패킷 수로 읽으면 안 된다.
상한 통계 Rule은 실험 코드에서 만든 기준선이며, 학습한 Rule 추천 LLM의 출력이나 사용자가 등록한 운영 규칙이 아니다.

### 6.3 최종 판정

```text
필요 수치가 모두 있는가?
 ├─ 아니오 → unavailable, 이상 여부는 NULL
 └─ 예 → 통계 Rule 실행 + IF 실행
          ├─ 하나라도 이상 → 이상
          └─ 둘 다 비이상 → 정상 판정
```

Rule이 이상이어도 IF를 생략하지 않았다. 코드에서는 두 결과를 순서대로 계산하고 OR로 결합한다.
동시 실행·GPU 병렬 처리·Rule 우선 차단 정책을 비교한 실험은 아니다.

## 7. 진행 절차와 저장·큐 검증

### 7.1 실제 수행 순서

1. 공개 ZIP 첫 1 MiB를 확보하고 conn 샘플 20,000개를 허용 필드로 투영했다.
2. 샘플을 시간순 학습·보정·시험 구간으로 고정했다.
3. 정상 학습 데이터로 scaler와 IF를 학습했다.
4. 정상 보정 데이터로 IF 임계값과 통계 Rule 상한을 계산했다.
5. 파일 기반 시험 추론을 수행하고 라벨과 비교했다.
6. 별도 임시 PostgreSQL에서 IoT 스키마를 생성했다.
7. 전체 샘플 20,000개와 정답을 분리 저장하고, 시험 구간 3,852개만 큐에 등록했다.
8. IoT 큐 소비자로 DB의 시험 관측을 읽어 실제 Rule·IF 판정을 저장했다.
9. 저장된 판정과 정답 표를 연결해 집계했다.
10. 동일 번들 재생, 임대 만료·재임대, 최대 재시도 및 불변성 검증을 수행하고 임시 DB를 정리했다.

이번 프로토타입은 **파일에서 수동 학습한 번들을 만든 다음 DB로 재생**했다.
원천을 먼저 운영 DB에 계속 축적하고 학습 작업 큐의 Trainer가 기간별로 학습하는 전체 운영 흐름을 실행한 것은 아니다.

### 7.2 저장 대상

| 대상 | 역할 |
|---|---|
| `powercode_iot.runs` | 번들·모델 hash와 고정 실험 메타데이터 |
| `powercode_iot.observations` | 투영 관측·시각·분할·품질 상태 |
| `powercode_iot.ground_truth` | 정답 라벨·공격 유형 |
| `powercode_iot.detection_queue` | 관측 ID와 실행 ID를 담은 별도 탐지 큐 |
| `powercode_iot.decisions` | 최종 판정, Rule·IF 개별 결과, 점수·임계값·근거 |

관측 저장과 큐 등록은 같은 트랜잭션으로 확정했다.
완료 처리에서는 현재 임대 token과 만료 여부를 확인하고, 큐 완료와 판정 저장을 같은 트랜잭션으로 확정했다.
최종 스키마의 고정 메타데이터·관측·정답·판정은 UPDATE·DELETE를 거절하고, 큐 상태만 변경할 수 있게 했다.

### 7.3 기능 검증 결과

| 확인 항목 | 결과 |
|---|---|
| 최초 관측 저장 | 20,000개 |
| 최초 시험 큐 등록 | 3,852개 |
| 큐 완료 `done` | 3,852개 |
| 미확정 판정 | 0개 |
| 실험 종료 시 pending / leased / dead | 0 / 0 / 0 |
| 동일 번들 재생 | 추가 저장 0, 중복 인식 20,000, 추가 큐 0 |
| 만료된 소비자의 완료·갱신·실패 처리 | 거절 확인 |
| 재임대 후 과거 token의 완료 처리 | 거절 확인 |
| 임대 만료를 3회 반복한 별도 시험 메시지 | dead 전환 확인 |
| 최종 SQL의 고정 run 수정·삭제 | 불변 trigger로 거절 확인 |
| IoT 단위 시험 / 기존 임대 회귀 시험 | 11개 / 4개 통과 |

큐의 `done`은 처리 결과가 저장됐다는 뜻이다. 모든 행에서 Rule·IF 수치 판정이 가능했다는 뜻은 아니다.
판정 불가 2,097개도 `unavailable` 결과를 저장한 후 큐 처리를 완료했다.
최종 SQL과 불변 trigger 검증은 별도 새 임시 DB에서도 확인했다.

## 8. 라벨 비교 결과

### 8.1 시험 구간 전체 결과

| 실제 라벨 | 이상 판정 | 정상 판정 | 판정 불가 | 합계 |
|---|---:|---:|---:|---:|
| 실제 이상 | **459** | 697 | 575 | 1,731 |
| 실제 정상 | 6 | **593** | 1,522 | 2,121 |
| 합계 | 465 | 1,290 | 2,097 | 3,852 |

판정 가능한 1,755개만 보면 TP=459, FP=6, TN=593, FN=697이다.
별도로 판정 불가 이상 575개와 판정 불가 정상 1,522개가 존재한다.
판정 불가를 TN으로 더하거나 정상으로 표시하지 않았다.

### 8.2 지표와 분모

| 지표 | 계산 | 결과 |
|---|---|---:|
| 정밀도, 판정 가능 행 기준 | `459 / (459 + 6)` | **98.71%** |
| 재현율, 판정 가능 행 기준 | `459 / (459 + 697)` | **39.71%** |
| 정상 오탐률, 판정 가능 행 기준 | `6 / (6 + 593)` | **1.00%** |
| F1, 판정 가능 행 기준 | `2×459 / (2×459 + 6 + 697)` | **56.63%** |
| 판정 가능 비율, coverage | `1,755 / 3,852` | **45.56%** |
| 판정 불가 비율 | `2,097 / 3,852` | **54.44%** |
| 전체 이상 기준 탐지율, end-to-end recall | `459 / 1,731` | **26.52%** |

F1은 기존 TP/FP/TN/FN에서 보고서 작성 시 산술 계산한 파생 지표다.
CLI의 기존 집계에는 정밀도·재현율·오탐률·coverage·end-to-end recall이 포함된다.
이 표는 **Rule OR IF의 결합 결과**이며, Rule 단독·IF 단독 성능으로 읽으면 안 된다.

### 8.3 판정 불가 원인

저장된 품질 표시에서 시험 구간의 다음 항목을 확인했다.

| 사용할 수 없었던 원천 필드 | 해당 행 수 |
|---|---:|
| `duration` | 2,097 |
| `orig_bytes` | 2,097 |
| `resp_bytes` | 2,097 |

동일한 행에 여러 항목이 겹치므로 세 건수를 합산하면 안 된다.
품질 표시의 `unavailable`은 결측뿐 아니라 숫자로 사용할 수 없는 값도 포함한다.
모든 항목을 실제로 제공하는 수치 벡터만 허용한 현재 정책이 높은 판정 불가 비율에 영향을 주었다.

## 9. 해석과 한계

### 9.1 확인한 사실

- 실제 IoT 연결 데이터를 읽어 저장·큐·추론·근거 저장·라벨 비교를 수행할 수 있다.
- 이상이라고 판정한 465개 중 459개가 이상 라벨이었다.
- 그러나 판정 가능한 이상 1,156개 중 697개를 놓쳤고, 이상 575개는 판정하지 못했다.
- 전체 이상 1,731개 중 탐지한 것은 459개이므로 실질적인 탐지 범위가 좁다.

현재 결과는 **오탐은 적지만 미탐과 판정 불가가 많은 기준선**이다.
정밀도 98.71%만 제시하면 실제 한계를 가리게 되므로, coverage 45.56%와 전체 이상 탐지율 26.52%를 함께 제시해야 한다.

### 9.2 이번 시험으로 입증하지 않은 것

| 항목 | 이유 |
|---|---|
| 전체 IoT-SFC 성능 | ZIP 시작 부분의 conn 샘플만 사용 |
| 모든 프로토콜·기기·공격 유형 일반화 | 대표 표본·전체 기간·외부 기기 평가를 수행하지 않음 |
| 운영 장애 전반 탐지 | 이번 정답은 제공된 정상·공격 라벨이며 일반 장애 정답 평가를 수행하지 않음 |
| 완전한 세션 독립 평가 | 시간·uid 분리만 적용하고 공격 세션 전체 분리는 수행하지 않음 |
| Rule·IF 중 어느 방법이 더 좋은지 | 단독 성능 비교·제거 실험을 별도로 집계하지 않음 |
| 추천 모델의 효과 | 피처·Rule을 고정 기준선으로 구성 |
| 실시간 목표 지연·처리량 | `--rate` 제어와 큐 기능을 확인했으며 반복 부하·단계 지연은 계측하지 않음 |
| 장애 전 예측·리드타임 | 공격 세션 시작 정답과 연결한 시계열 사건 평가를 수행하지 않음 |
| 원인 단계 설명 정확도 | 원인 처리 단계의 정답을 이용한 검증을 수행하지 않음 |
| 전체 서비스 운영 연동 | UI·알림·학습 작업 큐·승인 적용·서버 GPU 시험 미포함 |

연결 지속 시간과 송수신 합계는 완성된 연결 로그의 정보일 수 있다.
따라서 이번 결과를 연결이 진행되는 도중의 조기 탐지나 공격 발생 전 예측 성능으로 해석하지 않는다.
다른 seed·모델·피처·임계값 조합의 반복 평가나 신뢰구간도 산출하지 않았다.

## 10. 재현 방법과 산출물

### 10.1 실행 순서

전체 서버 명령과 읽기·변경 작업의 구분은 [IoT-SFC 실행 안내](../../../server/worker/iot_sfc/README.md)를 따른다.
서버용 이미지는 [전용 Dockerfile](../../../server/worker/iot_sfc/Dockerfile)로 빌드한다.

아래는 같은 기능 시험을 수행하는 CLI 예시다. 저장소 루트에서 시험 전용 Python 환경을 사용하고,
출력은 Git 제외 경로에 만든다. 기존 결과를 덮어쓰지 않도록 새 출력 디렉터리를 지정한다.

```bash
export PYTHONPATH=server/worker

# 파일 변경·공개 데이터 일부 다운로드. DB 변경 없음.
python -m iot_sfc sample --output research/evaluation/iot_sfc/runs/reproduction-01/sample --limit 20000

# 파일 읽기 검사. DB 변경 없음.
python -m iot_sfc inspect --csv research/evaluation/iot_sfc/runs/reproduction-01/sample/sample.csv

# 파일 변경·수동 학습. DB 변경 없음.
python -m iot_sfc prepare --csv research/evaluation/iot_sfc/runs/reproduction-01/sample/sample.csv --output research/evaluation/iot_sfc/runs/reproduction-01/bundle

# 파일 읽기·추론·평가. DB 변경 없음.
python -m iot_sfc test --bundle research/evaluation/iot_sfc/runs/reproduction-01/bundle
```

PostgreSQL까지 재현하려면 실행 안내에 따라 별도 IoT 스키마를 준비한다.
`DATABASE_URL`은 작업자 `.env` 또는 환경변수에서 읽고 값은 출력하거나 명령행 인자에 적지 않는다.

```bash
# DB 쓰기 전 번들 검사. --apply가 없으므로 DB 변경 없음.
python -m iot_sfc replay --bundle research/evaluation/iot_sfc/runs/reproduction-01/bundle

# DB 변경: 전체 관측·정답 저장, 시험 구간 큐 등록.
python -m iot_sfc replay --bundle research/evaluation/iot_sfc/runs/reproduction-01/bundle --rate 100 --apply

# DB 변경: 해당 번들의 큐 소비·판정 저장.
python -m iot_sfc detect --bundle research/evaluation/iot_sfc/runs/reproduction-01/bundle

# DB 읽기·집계.
python -m iot_sfc report --bundle research/evaluation/iot_sfc/runs/reproduction-01/bundle
```

위 `--rate 100`은 재현 예시의 저장 목표 속도다. 최초 기록된 실제 DB 검증에서는 `--rate 0`으로 속도 제한 없이 재생했다.
실측 초당 처리량이 100이었다거나 특정 지연을 달성했다는 의미가 아니다.

### 10.2 번들 파일

| 파일 | 내용 |
|---|---|
| `sample.csv` | 허용 필드와 평가 정답만 남긴 소량 CSV |
| `sample-manifest.json` | 배포 버전·부분 다운로드·표본 방식 |
| `observations.jsonl` | 정답을 분리한 투영 관측, 고정 분할·품질 표시 |
| `labels.jsonl` | 행 번호와 평가 정답 |
| `model.joblib` | 학습한 scaler·IF·IF 임계값·통계 Rule |
| `manifest.json` | 피처 순서·분할 경계·사용 건수·버전·파일 hash |

정확한 이번 번들의 파일 SHA256은 다음과 같다.

```text
observations.jsonl  945ebf87c3c3b337ec5e5c09a068eec3e8ce9d0dc7e43b6b7f45b8b057ccbf65
labels.jsonl        673c0f1216530b13d3a892bf6506c2d6401cd3c98591dca9c223ddcebc8de2a8
model.joblib        d88e77a958b29c42c2ec4b3a902fdbd3cf596553af216ca0baea0ae53ef7a306
manifest.json      2a6a74c5c134fa9c646b0788cd9fc314623abde038227583893da966130ab55f
```

이 hash는 **이번 실행에서 만든 로컬 산출물**의 식별 정보다. 공식 원본 ZIP의 무결성을 확인한 값이 아니다.
새 실행 ID와 환경으로 재현하면 manifest 및 모델 직렬화 파일의 hash가 달라질 수 있다.
자신이 생성한 신뢰하는 번들만 사용하고, 외부에서 받은 임의 joblib/pickle을 로드하지 않는다.

원본·샘플·모델·개별 관측·개별 판정은 Git에 추가하지 않았다.
실행 코드가 당시 로컬 미커밋 변경 사항이므로 위 기반 커밋 하나만 checkout해서 같은 경로를 재현할 수는 없다.
재현 시 이 보고서에 연결된 IoT 코드와 고정 패키지 환경도 함께 확보해야 한다.

## 11. 후속 실험 권장 순서

1. 원본 전체 파일을 확보·검증하고 기간·프로토콜·공격 세션별 분포를 확인한다.
2. 구간을 가로지르는 공격 세션까지 분리하고, 모델 선택용 validation과 최종 test를 별도로 고정한다.
3. 로그 종류별 실제 제공 필드에 맞춰 결측 처리 또는 별도 피처 집합을 설계하고 coverage를 먼저 개선한다.
4. 같은 고정 시험 표본에서 Rule 단독·IF 단독·결합 결과를 각각 비교한다.
5. 정밀도·오탐률과 함께 미탐·판정 불가·전체 이상 탐지율을 보고한다.
6. 탐지 품질을 확인한 뒤 운영 저장·학습 작업 큐·승인·조회와 연결하고 실제 서버에서 지연·부하를 계측한다.

위 항목은 후속 제안이며 이번 시험에서 구현·검증을 완료했다는 의미가 아니다.
